# Codex 执行提示词

## 使用方式

在 Codex 中打开 `learning-practice` 仓库工作区，提供同目录下的 `learning-practice_review_and_remediation.md`；如需参考竞争问题的独立复现，同时提供 `orphan_race_repro.py`。

下面的提示词可直接复制给 Codex。附件不一定会自动出现在 Codex 工作区，执行前应通过实际上传或本地文件确认它们可见。不要让 Codex 根据聊天中的文件名猜测路径。

## 完整提示词

你现在是 `learning-practice` 项目的维护工程师。请基于当前工作区代码，参考我提供的 `learning-practice_review_and_remediation.md`，直接开展复核、最小化修复和验证，而不只是再次给出建议。

项目仓库：https://github.com/zhuzhipeng-123/learning-practice

### 一、目标与基本原则

这是一个本机个人学习工具。我不希望过度设计。目标是修复真实缺陷、减少任务误判与错误学习、降低维护成本，而不是扩展功能数量或追求大型项目架构。

审查文档来自此前的静态审查，不是当前代码的权威结论；没有固定的原审查 commit，也没有完整应用实测背书。你必须自己核对当前实现。文档中的路径、函数名、状态和风险如果已过期，就以当前代码和测试为准，记录“已修复”“不适用”或“证据不足”，不要制造无意义修改。

### 二、先建立基线，但不要只停在计划阶段

1. 阅读 `AGENTS.md`（如果存在）、README、当前实施状态、依赖和测试配置、数据库迁移说明。确认实际启动方式与是否单应用进程。
2. 记录当前分支、commit 和工作区已有修改。保留我的未提交内容，不要清理或回滚它们。
3. 找到实际测试入口，运行能执行的相关基线测试。不能编造测试命令，也不能把旧文档中的通过数量当作本次结果。
4. 对 R01–R12 建立简短核对表：确认存在、已修复、不适用、待测量或待证据。关键结论写明实际文件与位置。
5. 给出本轮小范围修改计划后，继续执行已经具备条件的修改。对可以安全判断的问题自行选择最小方案，不要只返回“是否开始”。

### 三、第一优先级：R01、R02，以及 R03 配套测试

#### R01：来源同步状态恢复

完整追踪来源任务入库、内存注册、后台执行、状态查询、启动恢复和重试路径。

检查旧活跃集合快照是否可能导致：完成任务被改回可恢复；刚启动且正常运行的任务被误判为孤儿。

优先让状态查询保持只读，把恢复动作放到合适的恢复入口。协调任务注册与存活判断，使用条件更新保护状态与执行归属，并检查更新行数。只增加 `WHERE status IN (...)` 不应被当成完整修复，除非你已证明注册时序也安全。

锁只保护短临界区；不要持锁执行网络请求或等待任务完成；统一锁和数据库事务顺序。进程内锁不能被描述为支持多应用 worker。

必须测试：注册前窗口、检查期间完成、检查期间开始运行、同时重试、真实中断后的恢复，以及状态查询无写入副作用。

附带的 `orphan_race_repro.py` 只复现提取算法，不是项目集成测试。可参考其时序，但必须核对真实调用链，不能只运行附件就宣布已修复项目。

#### R02：模型长任务租约与所有权

完整追踪任务领取、生成、检查、修复、再次检查、失败记录和最终采用。

检查执行租约是否与多阶段总耗时冲突，`updated_at` 是否混合了执行身份和活跃时间，以及哪些中间响应写入绕过了所有权验证。

优先复用已有字段；确实需要时才做最少兼容迁移。区分稳定执行身份、活跃时间/租约与整条任务预算。保证正常长任务不会被错误抢占，真正失活任务仍可恢复。

单次 HTTP 分阶段超时不等于整条任务的绝对总耗时。租约续期或心跳不能让卡死任务无限存活，退出路径要回收资源；不要只把超时改大。

所有受执行归属约束的持久化写入都要在写入时检查身份，包括原始响应、格式修复、质量结果和失败信息。最终学习结果采用与任务采用状态应有一致的事务边界。

保留冻结输入、配置快照和历史版本语义。旧执行失去所有权后不能覆盖新执行，但也不要将“结果最多采用一次”夸大成“外部模型调用恰好一次”。没有可靠提供方幂等保证，就说明恢复时仍可能出现外部重复请求。

使用可控时钟和外部模型替身验证：正常长任务、不活跃过期、竞争领取、旧执行最终响应迟到、旧执行格式修复迟到、总预算耗尽、心跳退出以及快照不漂移。

#### R03：补真实内部路径测试

保留临时数据目录和数据库隔离，核对 `tests/conftest.py` 等是否默认替换内部调度。

关键测试要真实贯通“接口 → 调度 → 服务 → SQLite → 状态读取”，只替换飞书、模型等外部边界，不能替换正在验证的内部逻辑。

优先用 Event、屏障、可控执行器或时钟稳定构造时序，不用长时间 sleep 碰运气。保证测试结束后回收线程、连接和全局状态。

保留已有前端模拟回归。真实浏览器测试优先复用已有工具；如果缺少环境，不要为此新增庞大体系，提供可运行的服务测试和明确的人工浏览器验收步骤。

### 四、后续按收益实施，不为了清单做满而扩范围

- R11、R12：确认后完成低风险的来源数量修正和文档同步。先核对 `source_count` 是总数还是新增数，保持接口契约。测试数字只能来自本次实际执行。
- R04：先明确来源参考、模型检查、人工核验和争议提示。优先复用现有元数据改标签与说明，不改评分、每日计数、复习资格、答案暴露或跨日规则。只有有独立依据的样本才能标为已核验；模型生成后自评不算人工事实依据。
- R09：用现有日志补任务/执行 ID、阶段、耗时、错误类别与可用的使用量。不记录密钥或完整私人内容，不新建监控平台。
- R05、R06：先测程序文件扫描和复习查询。没有明确收益就不改。可以局部批量查询、限制无界历史读取；必须保留运行版本不一致时的写入保护。“推荐下一题”只能复用现有学习规则，不能变成新调度算法。
- R07：确认 CLI 确实先收完输出再限大小时，再局部修复。兼顾 stdout/stderr、超限、超时、解码和进程回收，保留 `shell=False` 与现有平台边界。
- R08、R10：仅在收益明确且很轻量时实施。不完整抢救快照不得冒充完整备份；路由只随相关业务修改局部整理，不做全仓库重构。

### 五、硬性约束

1. 不重写前端，不换数据库，不新增 Redis/Celery、微服务、通用 Agent、向量库/RAG、多用户权限、FSRS、在线判题平台或大型监控系统。
2. 不进行无关依赖升级、大面积格式化、机械拆文件或无必要抽象。已有相关设施不要求为了遵守本条而删除，本条限制的是本轮新增范围。
3. 不连接真实飞书做同步，不调用真实收费模型，不修改正式学习数据库，不导出或提交密钥和私人笔记。默认在临时数据目录与本地替身上验证。
4. 不关闭本机 Host/来源保护，不改成公网监听，不把进程内方案宣称为多进程安全。
5. 如需迁移，使用现有迁移框架，验证新建库与代表性旧库，保留历史关联和备份校验；说明回退限制，不在正式库上试错。
6. 不删除或覆盖我的未提交修改，不执行破坏性 Git 清理，不自动提交或推送，不使用吞异常、跳过关键测试、固定返回成功来掩盖问题。
7. 每完成一个相对独立修改就运行对应回归。遇到网络、依赖、凭证或环境限制，完成可验证部分并说明限制，不虚构通过结果。
8. 涉及数据破坏、生产调用、现有业务规则改变或大规模架构决定时，不擅自执行；记录未实施事项，但不要因此阻塞其余可以安全完成的修复。

### 六、最终交付

请交付实际代码修改和必要回归，不要只输出建议清单。优先更新已有实施状态文档，避免新增多份重复报告。

最终按以下结构汇报：

1. 实际分支/commit、基线情况、已保留的用户原有修改。
2. R01–R12 核对结果：已修复、已不存在、不适用、暂缓或仍未验证，以及真实证据位置。
3. 修改文件、每项修改原因、为什么采用这个最小方案。
4. 实际执行的测试命令与结果，区分通过、失败、跳过和未运行；说明原有失败与本次新增影响。
5. 是否有数据库迁移、部署步骤、API 或学习行为变化，以及回退限制。
6. 剩余风险、未做的可选优化和理由。

默认先把 R01、R02、R03 做扎实，再处理确认存在的低风险小修和局部改进；不要为了完成所有可选项目牺牲数据安全、可读性和可验证性。
