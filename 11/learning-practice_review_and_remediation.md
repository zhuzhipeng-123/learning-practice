> 项目：<https://github.com/zhuzhipeng-123/learning-practice>
> 整理日期：2026-09-21
> 文档用途：将本轮对话中的项目审查转成可以交给 Codex 执行的整改任务书。

## 0. 阅读说明与证据边界

### 0.1 这份文档是什么，不是什么

本文件是上一轮审查的结构化整理，不是对当前 `main` 的第二次独立审计，也不是已经合并的修复说明。

上一轮审查所述范围包括公开仓库中的应用入口、中间件、来源同步、模型调用与任务、复习页面、导出、部分前端回归测试和工程文档。上一轮没有成功拉取并运行整个项目，没有连接真实飞书、Agnes 服务或正式学习数据库，也没有记录可用于固定审查对象的 commit SHA。

因此，**所有文件路径、函数名、状态值和实现现象，都必须由 Codex 在实际工作区重新核对**。如果代码已经变化、问题已经修复，或前述推断不成立，应记录事实并跳过，不得为了符合本文而制造改动。

上一轮提及的测试数量来自项目文档，不是本次重新运行的结果。本文件不将任何历史测试数量作为验收门槛。

### 0.2 证据分级

| 类型 | 含义 | 执行方式 |
|---|---|---|
| 上轮静态发现，待当前仓库核对 | 上轮读代码发现了具体实现或风险点 | 阅读完整调用链，补回归或最小复现后判断 |
| 独立算法复现 | 附件脚本在临时 SQLite 中复现了提取算法的特定竞争时序 | 只能支撑该算法风险；仍要在真实项目路径验证 |
| 设计或产品语义风险 | 行为可能符合原设计，但容易误导或缺少边界 | 先澄清现有规则，优先改标签、说明、局部行为 |
| 待测性能风险 | 静态结构存在增长成本，但未测量实际瓶颈 | 先测量；没有明显收益就不做性能重构 |
| 可选增强 | 可以提高可维护性，但不是已证实缺陷 | 仅在成本低、收益明确且不扩大范围时实施 |

### 0.3 Codex 的执行边界

- 可以读取代码、添加定向测试、运行隔离测试、修改必要文件，并在确有必要时设计兼容迁移。
- 不得读取或修改正式学习数据来做破坏性验证，不得自动执行真实飞书同步或收费模型调用。
- 不得输出、提交或记录密钥、访问令牌、完整私人笔记、用户真实答案等敏感内容。
- 不得删除用户未提交的修改，不得使用 `git reset --hard`、`git clean -fd` 等方式清理工作区，不得自动推送远程分支。
- 网络、依赖或外部服务不可用时，先完成可离线验证的部分，明确记录未验证项；不得把“没有执行”写成“通过”。
- 不得擅自改变复习通过条件、每日计数、跨日恢复、历史归属、参考答案暴露后的计分规则。

## 1. 总体结论与目标

### 1.1 总体判断

沿用上一轮审查的总体判断：这个项目不需要推倒重写。现有 FastAPI、Jinja2、原生 JavaScript、SQLite 的组合，与本机单人学习工具的定位相匹配。执行时应先确认当前仓库仍采用这一结构。

相比继续增加功能，下一阶段更值得解决的是：

1. 后台任务状态不能被误判，重试不能无谓地产生重复执行。
2. 模型生成、自动检查和人工核验应有清楚的可信边界。
3. 历史数据增长后，日常练习入口仍然直接，维护和排错不应越来越费劲。

### 1.2 需要保留的能力

上一轮审查观察到的以下能力属于与真实需求相关的复杂度，应核对后保留，不得以“简化”为理由删除：

| 能力 | 为什么保留 |
|---|---|
| 来源版本、历史素材关联 | 保证历史作答仍能追溯当时依据 |
| 迁移前备份、事务迁移、版本检查 | 保护已有学习记录，避免更新破坏数据 |
| 完整导出的数据库、外键、附件校验 | 防止生成表面成功、实际不能完整恢复的备份 |
| 模型输入冻结、配置快照、请求关联 | 保证任务恢复和结果解释使用一致的输入 |
| 迟到结果检查、最终采用条件 | 防止旧执行覆盖新状态 |
| 本机 Host 与写请求来源检查 | 保持当前本机部署边界 |
| 现有复习、暴露、计数和跨日策略 | 这些是产品规则，不应与技术整改捆绑修改 |

如果某项能力在当前版本不存在或实现不同，应如实更新这份判断，而不是假设它已经具备。

### 1.3 本轮成功标准

本轮改造成功，不以新增多少功能、文件、类或测试数量衡量，而以以下结果衡量：

- 能稳定复现并修复已经确认的竞争时序。
- 正常活跃任务不会仅因旧快照或错误租约判断被重新领取。
- 丧失所有权的旧执行不能继续修改受保护的任务结果或学习状态。
- 原有数据能够继续读取，现有关键学习行为没有发生未声明变化。
- 模型评价的依据在界面和测试中表达得更诚实。
- 所有性能优化都有测量依据或明确的无界查询问题支撑。
- 没有新增与当前规模不相称的基础设施。

## 3. R01：来源同步状态恢复的竞争窗口

### 3.1 复核位置

优先阅读：

- `app/services/source_refresh.py`：`_mark_orphaned_runs()`、任务注册、状态查询、启动恢复、重试入口。
- `app/services/wiki_alignment.py`：任务执行及最终状态写入。
- 当前事务封装、来源同步接口和应用生命周期代码。

不要只看单个函数。需要画清楚以下实际顺序：

```text
创建数据库任务 → 注册内存执行句柄 → 调度后台执行
        ↘ 状态查询 / 启动恢复 / 显式重试 ↙
                    更新任务状态
```

### 3.2 上轮观察到的风险

上轮所述逻辑先读取内存中的活跃任务集合，再读取数据库中的 `queued/running` 记录，随后把“不在活跃集合中”的候选更新为 `recoverable`。这些步骤可能基于不同时刻的状态。

可能的时序一：

```text
A：读取活跃集合，此时尚未看到任务
B：注册任务，任务开始并执行完成
A：继续使用旧判断，将完成状态覆盖成 recoverable
```

可能的时序二：

```text
A：读取活跃集合，此时尚未看到任务
B：注册任务，任务仍在正常运行
A：继续使用旧判断，将正常 running 改成 recoverable
```

附件 `orphan_race_repro.py` 验证的是提取算法在上述交错下的行为，并说明：**仅增加 SQL 状态条件可以保护已经完成的任务，却不足以避免把刚注册、仍然运行的任务误判为孤儿。**

### 3.3 最小修改方向

**第一步：让状态查询回到只读职责。**

检查是否可以把恢复动作集中到启动恢复与显式重试入口。若轮询接口当前会修复数据库状态，先评估移除该副作用对前端恢复提示的影响，避免只删写入却让真正中断任务永远不可恢复。

**第二步：协调任务注册与孤儿判定。**

在现有单进程设计下，优先使用现有同步机制，明确“任务已入库但尚未登记执行句柄”这一阶段如何受保护。复核活跃注册表究竟按来源、任务运行 ID 还是其他键索引；必要时用准确的执行标识判断，避免把同一来源的不同运行混为一谈。

不得在执行网络请求、完整同步或 `Future.result()` 等长时间等待期间持有全局锁。锁与数据库事务的取得顺序必须一致，防止用死锁替代原竞争问题。

**第三步：用条件更新保护状态和执行归属。**

更新必须验证记录仍处于允许恢复的状态，并在需要时核对执行归属。事务开始前的旧快照不能作为唯一依据。检查实际受影响行数，不能把未发生更新当成成功恢复。

**第四步：明确进程边界。**

确认项目启动方式。如果当前只支持单应用进程，就在运行说明和测试中写清楚，不要声称进程内锁能够支持多个 worker。除非项目已经明确使用多进程，否则本次不要引入分布式调度设施。

### 3.4 必须满足的不变量

- 完成或其他终态不能被旧的恢复判断覆盖。
- 正常活跃运行不能被判断成孤儿并无谓地重复调度。
- 真正中断且没有活跃执行的任务仍可恢复。
- 连续查询状态不会改变数据库里的任务状态或更新时间。
- 两个页面同时重试时，只产生一个有效的新执行所有者。
- 修复不造成“任务永远 running、无法恢复”的反向问题。

### 3.5 定向测试

| 测试 | 如何控制时序 | 预期 |
|---|---|---|
| 已入库、尚未注册 | 在注册前设置可控屏障 | 不误判为可恢复，不重复调度 |
| 恢复检查期间完成 | 在候选读取与最终处理之间完成任务 | 保留实际终态 |
| 恢复检查期间启动 | 在同一窗口注册并启动任务 | 保留正常活跃状态 |
| 双页面重试 | 两个独立请求争用同一任务 | 至多一个有效执行所有者 |
| 进程中断后恢复 | 清除执行上下文，保留临时库记录 | 可以走受控恢复路径 |
| 纯状态轮询 | 对比查询前后数据库快照或写语句计数 | 不出现状态修改 |

测试应使用 `Event`、屏障、可控执行器或精确的测试挂钩，避免依赖长时间 `sleep()` 碰运气。可以替换外部飞书响应，但必须保留真实接口、服务、事务和状态写入路径。

## 4. R02：模型长任务、租约与旧执行写入

### 4.1 复核位置

- `app/services/model_jobs.py`
- `app/services/module_jobs.py`
- `app/services/question_quality.py`，重点核对 `checked_quality_format()` 等直接写请求记录的分支。
- `app/adapters/agnes.py`
- 当前模型任务表、任务领取、恢复入口、配置冻结和最终结果采用事务。

### 4.2 上轮观察到的风险

上轮所述实现使用约五分钟的租约，并通过 `updated_at` 判断 `running` 任务是否可重新领取，但主流程执行期间没有持续更新活跃时间。

实际任务可能包含多个串行步骤：

```text
生成问答 → 质量检查 → 修正 → 再次检查
```

格式修复还可能增加额外请求。因此，单轮请求能在自己的超时范围内完成，并不表示整个任务一定在租约内结束。

要区分三个不同概念：

| 概念 | 解决的问题 |
|---|---|
| 单次 HTTP 分阶段超时 | 连接、读取、写入、连接池等待等局部等待不能无限延长 |
| 整条任务的总时间预算 | 多阶段、修复和等待累计不能无限延长 |
| 执行租约与所有权 | 谁有权继续执行和采用结果，何时允许恢复 |

HTTPX 的读取超时并不是整个请求的绝对墙钟时间上限。实现时应核对当前 HTTP 客户端版本和用法，不得把 `read_timeout=90` 直接当成“整次调用最多九十秒”。

### 4.3 必须先区分的两个目标

**结果最多采用一次，不等于外部模型请求一定只调用一次。**

最终写入有所有权检查，可以阻止旧结果污染学习状态；但发生超时、网络不确定性或合法恢复时，旧的外部请求可能仍在进行。除非模型提供方支持并且应用实际使用了可靠幂等机制，不能宣称实现了端到端“恰好调用一次”。

本次最低目标是：

1. 正常活跃执行不被错误抢占。
2. 合法恢复后的旧执行不能覆盖新执行的结果或记录。
3. 无限等待或无限续期被明确限制。
4. 无法完全避免的外部重复调用风险在诊断与说明中被如实表达。

### 4.4 最小修改方向

**A. 将执行身份与活跃时间分开。**

优先复用已有字段。确实缺失时，可增加少量字段表达“本次执行标识”和“租约/活跃时间”，但不要预先创建完整调度框架。字段名应遵循当前项目，不必机械采用 `owner_token`、`heartbeat_at` 等示意名称。

执行身份应在本次领取期间稳定；心跳或活跃时间变化不能让身份比较失去意义。

**B. 协调整体预算与租约续期。**

根据当前最长合法工作流定义有限的总预算和修复次数。不能仅在每阶段结束时刷新活跃时间，却允许单个阶段超过租约且无人续期；也不能让心跳在任务卡死后永久续约。

选择当前架构里最小的实现：阶段边界刷新配合明确阶段上限，或确有需要时增加受控心跳。心跳生命周期必须绑定当前执行，并在完成、失败、取消、失去所有权或超过总预算后停止。

总预算的判断应使用适合计算耗时的时钟；持久化时间格式继续遵循项目已有约定。测试覆盖过期边界，避免时区或系统时钟变化导致错误抢占。

**C. 枚举并保护所有持久化写入。**

不仅检查最终成绩，还要核查模型原始响应、格式修复记录、质量检查结果、失败信息和任务状态。所有受执行归属约束的写入，应在实际写入时确认当前身份，而不是仅在长流程开始时检查一次。

对最终结果采用，检查“写业务结果”和“更新任务采用状态”是否处于一致的事务边界。条件更新失败时，不能留下半份学习结果。

**D. 保留输入冻结和配置快照。**

同一逻辑任务的重试、恢复应遵守既有输入与配置策略，不得在恢复时默默换成最新题目或最新模型配置。

**E. 增加有限诊断，不增加运行平台。**

记录任务 ID、执行标识、阶段、耗时、恢复原因和是否丧失所有权即可。令牌使用量只在提供方返回且能可靠关联时记录；不要捏造 token 数或成本。

### 4.5 验收测试

| 场景 | 预期 |
|---|---|
| 多阶段任务仍正常活跃 | 不因旧固定租约而被重复领取 |
| 单个阶段较长 | 租约策略与合法阶段上限一致 |
| 任务真正失活 | 在明确条件下可以恢复，不永久占用 |
| A 失去所有权后返回，B 已接管 | A 的最终结果不能覆盖 B |
| A 的格式修复或质量响应迟到 | A 的中间写入同样被拒绝 |
| 两个请求同时恢复 | 只有一个成功获得新执行身份 |
| 达到总预算或修复上限 | 明确失败或进入现有可恢复状态，不无限循环 |
| 失败、完成或丧失所有权 | 心跳、线程或定时资源能够退出 |
| 请求/配置在前台变化 | 已冻结任务仍遵循自身快照 |
| 缺少 token 使用量 | 不崩溃，不填假数 |

测试使用可控时钟和本地模型替身，不能为了验证五分钟过期而真的等待五分钟。状态名字按当前代码使用，不为本文示例新增无必要状态。

## 5. R03：让测试覆盖真实内部连接处

### 5.1 复核位置与问题

上轮审查发现，`tests/conftest.py` 的自动 fixture 同时承担数据目录隔离，并默认替换 `app.routes.api.queue_source_refresh`。

数据隔离应继续保留；内部调度默认被替换则需要审视。它可能使接口测试验证了参数和返回值，却没有验证实际注册、执行、数据库状态和轮询之间的配合。

这不代表所有现有测试都无效。应逐项确认哪些测试主动使用真实路径，哪些测试只验证局部契约。

### 5.2 修改要求

- 保留临时数据目录、临时数据库和环境变量隔离。
- 将“内部业务不执行”的替身改成测试显式选择，或为贯通测试提供清晰、默认不会误用的 fixture。
- 只替换飞书、模型和必要系统外部边界；R01/R02 的关键调度、服务、事务必须真实执行。
- 不一口气重写全部测试。先为最高风险路径增加或修正少量定向测试。
- 测试结束后回收线程池任务、关闭连接、恢复全局注册表，防止不同测试互相污染。

### 5.3 应具备的测试层级

| 层级 | 重点 | 适当替身 |
|---|---|---|
| 单元测试 | 条件更新、状态判定、序列化、超时预算计算 | 可以替换依赖 |
| 服务集成测试 | 真 SQLite、事务、任务领取和结果采用 | 替换外部服务，不替换被测业务 |
| 路由贯通测试 | HTTP → 调度 → 数据库 → 状态读取 | 外部服务采用本地确定性响应 |
| 浏览器关键流程 | 提交后刷新、重复点击、跨页面重试、错误恢复 | 本地应用＋受控外部返回 |

上一轮提及的 `tests/browser_request_regressions.cjs` 属于已有模拟环境回归，应保留其价值，但不要将其描述为已覆盖真实浏览器端到端行为。

真实浏览器测试优先复用已有环境。若仓库没有相应依赖，不应只为本次整改引入庞大浏览器测试体系；先交付路由/服务贯通测试和人工验收步骤，并明确未执行的浏览器项。

### 5.4 测试质量标准

关键回归应能在被确认的旧实现上失败、在修复后通过，且失败原因正是目标缺陷。禁止通过跳过测试、扩大容忍范围、吞异常、固定返回成功或 mock 掉被测逻辑来达成“全绿”。

## 6. R04：区分参考来源、自动检查和人工核验

### 6.1 复核位置与风险

优先阅读 `app/services/reference_state.py`、参考状态的调用者、前端标签、评价提示词和 `reference_correction` 相关逻辑。

上一轮所述行为是：没有显式核验记录时，`source_kind == 'feishu'` 会让 `verified` 默认为真。这个规则可能本来就表示“用户登记的可信来源”，但名称和展示容易让人理解为“每项结论已经确认正确”。

应先明确当前 `verified` 被用于哪些地方：只影响显示，还是还控制出题、评分、计数、复习通过或结果采用。没有完成这个检查之前，不得直接批量改布尔值。

### 6.2 最小改法

优先保留存量行为，用现有元数据表达不同证据来源：

| 显示含义 | 可用于说明什么 | 不能暗示什么 |
|---|---|---|
| 来源笔记参考 | 内容来自指定来源和版本 | 内容已被逐项人工证实 |
| 模型检查通过 | 通过当前自动规则或模型检查 | 已保证无事实错误 |
| 人工核验通过 | 指定版本经过人工核对 | 后续新版本自然继承人工确认 |
| 存在争议或待校正 | 当前依据需要复核 | 系统已确定用户回答错误 |

这些是不同维度，不一定必须改成一个互斥枚举。可以使用“来源标签＋核验标签＋争议提示”，避免为了四行文案新建复杂状态机。

本次默认不改变原有评分与通过规则。涉及是否阻止计分、是否改变复习结果的行为，先写成单独产品建议；不能藏在文案修改里顺带实施。

### 6.3 保留历史与版本边界

- 参考修正继续关联当时的来源或题目版本。
- 不直接覆盖飞书原文来抹平争议。
- 不让新核验状态追溯改写旧作答的依据。
- 已有历史记录缺少新标签信息时，显示为“未记录/未知”，不要推断为人工确认。
- 读取展示时不能为了补标签而悄悄批量写库。

### 6.4 建立小型、可靠的模型回归样本

目标是沉淀约 20–30 个有独立依据的样本；第一批可以更少，但必须真实可靠。不能为了凑数量，让模型自己生成答案再宣布自己已经人工验证。

建议覆盖：参考答案漏前提、示例输出与解释矛盾、用户采用另一种正确表述、图片是关键依据却没有被读取、追问未答却被总结为已掌握、证据不足却输出确定结论、无效 JSON、超时与格式修复。

最小样本字段可按现有结构裁剪：

```text
case_id
错误类型 / 标签
输入与所用参考版本
期望行为
不允许出现的行为
依据或核验说明
是否允许自动判断
```

自动结构校验和人工核验样本要分开：程序能验证 JSON 格式，不代表它能自动证明专业结论正确。缺少人工依据的样本应标为待核验，不能伪装成黄金标准。

### 6.5 验收

无核验记录的来源笔记不会被界面标成“人工核验”；自动检查与人工确认不会混淆；旧记录仍能读取；核验不会错误跨版本继承；现有计分、计数和复习规则不发生未经声明的改变。

## 7. R05：程序文件扫描与运行版本保护

### 7.1 复核位置

`app/services/runtime_state.py` 中的 `RuntimeVersionGuard`，以及状态轮询、静态资源和写请求经过该中间件的路径。

上轮观察是每次请求递归遍历程序文件，读取元数据并排序，与启动时快照比较。这个设计用于防止代码更新后，旧进程与新模板、脚本混用。

### 7.2 不要直接删掉保护

它防止的是数据一致性问题，不是纯粹的开发便利功能。不能只因为看到文件遍历就认定必须删除，也不能简单缓存所有检查、留下更新后继续写数据的窗口而不解释风险。

### 7.3 最小实施步骤

先在当前工作区记录文件数、单次扫描耗时、一次页面加载和轮询周期的扫描次数。用相同条件比较修改前后，不凭印象宣称性能提高。

如果耗时很小，保留现状即可。若轮询成为明确开销，优先在 R01 将状态查询改为只读后，评估减少这些只读请求的重复工作。写请求、关键页面和资源版本不一致时的阻断行为必须保持。

优先复用现有检查函数或更新流程，不新增长期运行的文件监听服务。

### 7.4 验收

- 程序或模板被更新后，旧进程的受保护写入仍能被阻止。
- 用户仍能看到明确的重启提示。
- 正常只读状态查询不会制造不必要写入。
- 若做优化，报告包含测量方法、样本与前后结果；若不做，说明“未测到值得整改的成本”。

## 8. R06：复习页查询与“下一题”入口

### 8.1 复核位置

`app/routes/pages.py` 的 `review_page()`，以及相关查询函数、复习模板和前端排序行为。

上轮观察是先一次读取复习轮次，再在 Python 中筛选排序，并逐条查询“今日有效通过”和“近期看过答案”。历史结束轮次也在读取范围内。

### 8.2 先修查询边界

在临时库构造有代表性的历史规模，记录 SQL 次数和耗时。样本量用于测试，不代表用户真实拥有这些记录。

优先将活动轮次、历史轮次和必要筛选下推到 SQL；把今日通过、近期暴露等信息批量读取，消除随每条记录增加的往返查询。避免为合并查询产生错误的多表重复计数。

确有需要再分页，分页必须有稳定排序和唯一字段兜底。先看查询计划，再增加与真实过滤条件匹配的索引；不要盲目给所有列建索引。

### 8.3 再考虑轻量的推荐入口

“推荐下一题”只能是展示建议，不是新调度算法。可以复用现有状态，优先显示今天适合独立作答、尚未完成且需要加强的题目。

不得擅自规定新的掌握阈值、间隔天数、暴露冷却时间或通过条件。已有规则是什么，就以什么为依据；没有依据的推荐标准先留在建议中。

原有列表和用户主动选题能力应保留，不必重排整页或重写前端。

### 8.4 验收

查询次数不随结果条数线性增加；分页前后没有重复或漏项；活动与结束轮次的边界正确；今日通过和答案暴露提示与修改前一致；“下一题”入口不改变实际计分资格。

## 9. R07：限制 CLI 输出的真实收集量

### 9.1 复核位置与风险

上轮在 `app/adapters/lark_cli.py` 观察到：先通过 `capture_output=True` 收集完整输出，再检查约八百万字节上限。

这种检查能拒绝处理超大结果，却不能阻止在检查之前已经发生的内存占用。应核对 stdout、stderr 是否都有保护，以及输出限制指单通道还是合计大小。

### 9.2 最小修改要求

采用有限读取或适合当前平台的受控缓冲方式，在达到上限时主动结束进程并回收资源。保留现有超时和参数数组调用方式，不引入 `shell=True`。

实现应同时处理 stdout、stderr，防止一侧管道写满造成死锁；处理分块 UTF-8 的解码边界；超限或超时后保留有长度上限、经过脱敏的诊断信息。退出、等待和资源关闭应覆盖成功与异常路径。

优先遵守项目当前支持的系统范围。不要引入只在某一平台可用的进程处理方式后，仍声称支持原有其他平台。

### 9.3 验收

正常输出成功；stdout 超限失败；stderr 超限失败；双通道持续输出不死锁；超时能退出；多字节字符分块不损坏正常结果；非零退出码可诊断；不会遗留测试子进程。

不要将无限流量或破坏性进程用于正式环境验证，使用本地受控测试脚本即可。

## 10. R08：完整备份与不完整抢救快照分开

### 10.1 定位

`app/services/exports.py` 及现有维护命令。上轮观察到完整导出会校验数据库和历史附件，附件缺失或损坏时拒绝完整导出。

该行为本身是保护，不应为了“导出总能成功”而削弱。

### 10.2 可选的最小增强

只有确实需要故障抢救时，新增一个维护命令或复用现有工具，生成明确标记为“不完整”的数据库快照和缺失/损坏清单。默认不必新增 UI。

快照必须采用适合 SQLite 当前运行状态的一致性备份方式，不能在 WAL 模式下随意复制主数据库文件并把它当作可靠备份。复用已有备份能力，不重复发明。

清单应说明不完整原因、未包含附件、创建时间、数据库版本和恢复限制。不应在日志中暴露无必要的私人内容或系统绝对路径。

### 10.3 验收

严格完整备份仍会阻止不完整结果；抢救路径不会显示“完整备份成功”；原数据库和附件不被修改；生成内容可检查；支持和不支持的恢复方式有清晰说明。

若没有真实需求或恢复格式会显著增加维护成本，记录为暂缓即可，不算整改未完成。

## 15. 数据与部署：全程适用的底线

### 15.1 数据库变更

若 R02 确实需要字段，先检查迁移框架与旧版本支持范围。采用兼容、可解释的迁移，避免为了局部修复重建全部表。

新旧数据都需要考虑：历史执行没有新身份字段时如何读取，正在运行但应用重启后的记录如何恢复，空值是否有明确含义。

必须在临时数据库或明确的测试副本上验证新建库和代表性旧版本迁移，检查外键、数据数量、历史关联和现有备份校验。不得拿正式库直接试错。

回退不等于安全地倒跑 schema：有迁移时应说明回退限制和如何从迁移前备份恢复，不承诺未经测试的无损降级。

### 15.2 本机使用边界

本轮不新增用户体系，不改成公网服务，不把监听地址改成公开访问，不关闭 Host、来源检查或其他现有保护。

如当前启动文档允许多个应用 worker，应核对进程内任务注册表与锁是否支持这一用法。不能一边采用单进程协调修复，一边继续默认声称支持多 worker。

### 15.3 环境与隐私

不读取真实密钥来验证错误日志，不触发真实付费调用，不将真实学习数据库提交到测试样例，不在截图或报告中暴露私人内容。

依赖缺失时说明缺失，不盲目升级框架、锁文件或整个运行环境。确需安装时使用项目既有环境与锁定版本，不全局升级。
